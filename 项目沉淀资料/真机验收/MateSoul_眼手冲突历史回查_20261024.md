## 当前结论

已找到取消眼手功能之前的实际代码，确认输入链路发生了实质变化。
历史 HUD 通过 PICO 原生 `pinchTouched` 与 XRI `ActionBasedController` 处理点击；
当前 HUD 使用自定义捏合迟滞，并把握拳状态、关节有效性和触碰占用作为准入条件。
这些差异可以解释部分点击取消或释放不及时，但尚未获得本次真人卡死时的原始输入，
不能把源码差异直接当作根因，也不能断言旧版完全没有冲突。

本轮只加入诊断日志，尚未修改交互行为。此前“86项检查、100次点击”使用处理后的
布尔/姿态注入，不包含真实 PICO 手势样本，不能作为本次真人故障已经修复的证据。

|---|---|---|---|
| 眼手按下/松开 | `<PicoHandInteraction>{RightHand}/pinchTouched`；SDK 阈值 `>0.8` | `IsPinching`：进入 `>=0.75`，保持 `>0.55` | 原生已松开而自定义仍按住 |
| 握拳准入 | HUD 原生点击不依赖 `Closed` | 眼手 `CanPinch` 和触碰 `CanPoke` 都拒绝 `Closed` | 同一个握拳迟滞可能同时禁用两种 HUD 输入 |

`PicoHandInputSetup` 的 BYTE `scale(factor=255)` 仍存在。原生 SDK 把 bool 0/1 写入
BYTE 控件，回放必须包含该处理器；不能把未校正的 byte 值当作真实按钮读数。

本轮在空 Play 模式场景回放实际 SDK `UpdateHand`、既有 BYTE 处理器、原生 InputAction
和历史 `ActionBasedController`。6个模拟原始样本通过，退出0，36.9秒：

| 样本 | SDK pinchValue | SDK graspValue | 原生pinchTouched | 历史UI按下 |
|---|---|---|---|---|
| 0 | 0 | 0 | 0 | 0 |
| 1 | 0.9 | 0.9 | 1 | 1 |
| 2 | 0.7 | 0.6 | 0 | 0 |
| 3 | 0.9 | 0.6 | 1 | 1 |
| 4 | 0.7 | 0.6 | 0 | 0 |
| 5 | 0 | 0 | 0 | 0 |

这验证了原生捏合减弱到0.7时会释放，graspValue=0.6不会阻止历史眼手输入。
样本由探针构造，未包含当前真人故障，不能代替头显传感器验收。
两次非Play模式采样因Editor输入路由无效而废弃，没有把它们当作历史实现失败。
